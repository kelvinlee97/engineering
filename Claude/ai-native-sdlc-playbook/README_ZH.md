## 一句话总结

AI 加快了实现代码的速度，但规划、审查、部署和治理仍可能停留在人工作业速度。Anthropic
提出的 AI 原生 SDLC，让每个阶段产出一个已提交、机器可读的工件，由下一阶段直接消费；人则把判断力
集中在明确的审批关口，而不是亲手完成每一次交接。

目标不是无限制自治。Agent 应在版本化政策、确定性检查、最小权限、沙箱和受保护的部署关口内运行；
涉及风险与判断的决策仍由人承担责任。

## 由工件组成的生命周期闭环

| 阶段 | 提交的工件 | 主要变化 |
| --- | --- | --- |
| 规划 | `intent.md` | 直接记录原始问题、目标结果、约束和待定问题。 |
| 设计 | `spec.md` | 把已接受的意图转成需求与设计，并在生成时应用组织政策。 |
| 构建 | `plan.md`、代码和测试 | 先审查实现计划，再生成代码；让仓库知识贴近代码。 |
| 测试 | 测试、构建、截图和 eval 结果 | 为 agent 提供快速反馈闭环，并持续验证 agent 配置。 |
| 部署 | PR 和审查发现 | 分层自动审查，保留分支保护，把人工审批留给关键改动。 |
| 维护 | 事故记录和新的 `intent.md` | 确定性检测问题，让 agent 通过受控路径诊断，再把结果送回规划阶段。 |

Git 历史由此成为审计轨迹：谁提出了什么、agent 产出了什么、应用了哪项政策，以及谁批准了结果。

## 六个阶段

### 1. 规划：一次记录真实意图

需求发起人与 agent 讨论后，把结果写入 `intent.md`。Product owner 修正并接受后，工作才进入下一阶段。
工件应说明问题、预期结果、受影响的用户和系统、约束，以及尚未解决的问题。

可以先在产品仓库建立 `intent/` 目录。只有当同一意图横跨多个仓库时，独立 intent 仓库才值得维护。

可观察的指标包括：

- 从首次讨论到提交 intent 的时间
- 进入设计阶段的 intent 比例
- 设计或实现开始后需求仍被修改的次数

### 2. 设计：在编写规格时应用政策

Agent 根据已接受的 intent 生成 `spec.md`，并通过版本化 skill 或指令应用安全、合规、品牌和 UX 政策。
Product owner 审查结果，与政策负责人解决被标记的冲突，并决定是否继续推进。

政策检查因此前移：问题会在设计仍容易修改时暴露，而不是拖到后期审查才发现。

### 3. 构建：实现前先批准计划

工程师让 agent 生成 `plan.md`，明确涉及的文件、执行顺序、风险和验证方式。工程师质疑并批准计划后，
实现才开始；实际实现如有偏离，计划也要同步更新。

把持久的仓库知识保存在简短、经过审查的 `CLAUDE.md` 中，包括构建与测试命令、约定、架构和常犯错误。
需要在组织内重复应用的政策应写成 skill，不要让仓库指令无限膨胀。

并行 session 应使用独立 Git worktree，并处理互不冲突的文件。可从两到三个任务流开始；真正的上限是人的
审查能力，而不是 agent 的生成速度。

### 4. 测试：让验证成为 agent 自己的反馈闭环

为任务提供可运行的完成标准：测试和构建各有一个简单命令，UI 工作还应提供视觉对比。Agent 在交给人
审查之前，先运行检查并修正自己的工作。

修复 bug 时，先用测试稳定复现失败，再在修复实现期间保护该测试不被修改。与此同时，当 agent 指令、
prompt、工具或模型变化时运行持续 eval。普通测试检查产品，eval 则检查这套开发系统。

### 5. 部署：自动化审查，但保留硬性关口

按正确性、安全、性能和政策合规等关注点执行多个聚焦的审查，再合并发现，让人优先判断分歧和高风险区域，
而不是同等强度地逐行重读所有生成代码。

逐步引入流水线自治：

1. 从构建失败分类、变更日志草稿等只读任务开始。
2. Agent 的改动只能通过 Pull Request 和分支保护进入代码库。
3. 在沙箱中运行任务，并使用短期、最小权限凭据。
4. 按环境把部署与回滚暴露为 allowlist 工具。
5. 开发环境可以比生产环境拥有更高自治程度。
6. 生产关口继续由人控制，并定期演练回滚。

### 6. 维护：从生产环境闭合循环

使用确定性监控而不是模型来检测控制带越界，再按等级响应：轻微偏差只记录，更大偏差触发只读诊断，
最高等级也只能创建 PR 或执行预先批准的 runbook。

Agent 把异常、证据、影响和待定问题写成新的 `intent.md`。Service owner 负责分类，正常审查关口继续有效；
修复发布后再增加回归 eval，降低同类事故重复发生的概率。

## 治理原则

- 为每种工件指定唯一 source of truth；若旧系统仍是权威来源，应链接到精确 commit。
- 把指令、skills、hooks、权限规则和控制带配置当作代码进行版本管理与审查。
- 确定性检查负责强制执行，agent 负责判断与诊断。
- 自动任务使用独立身份、最小权限，且默认不持有生产访问权。
- 受监管、关键、破坏性或影响生产的决策继续由人批准。
- 衡量返工、首次 CI 成功率、审查时间、变更失败率和重复事故，而不是代码生成行数。

## 可落地的采用顺序

不要一开始就自动化整个闭环。更小的起步方式是：

1. 先把 build、test 和 lint 变成简单可运行的命令。
2. 增加一份简短且持续维护的 `CLAUDE.md`。
3. 对有意义的改动要求审查 intent 和实现计划。
4. 为 agent 建立本地反馈闭环，并针对反复出现的问题增加 eval。
5. 在 CI 中加入只读故障分类和聚焦的 PR reviewer。
6. Agent 的写操作只能经过现有审查与部署关口。
7. 选择一个稳定、低噪声的生产信号，闭合第一条维护循环。

## 批判性阅读

这是 Anthropic 围绕 Claude 产品编写的运行模型，因此其中的产品选择不能视为厂商中立证据。更通用、
值得复用的思想是：明确工件、政策即代码、快速反馈、最小权限、确定性强制执行、可追踪审批，以及只有在
验证与回滚足够可靠后才逐步扩大自治。

## 核心结论

AI 原生开发不是单纯加快写代码，而是重新设计整个交付系统。最有价值的变化，是让每个阶段留下可审查的
工件，让自动化在定义清楚的关口之间推进工作，而人把注意力留给意图、风险与责任。
